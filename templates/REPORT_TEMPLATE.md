# 🔄 [ABAP 리팩토링] {프로그램명} — As-Is vs To-Be

> 이 파일은 한 건의 리팩토링 작업 리포트 템플릿이다.
> 새 작업: `refactorings/_TEMPLATE_YYYYMMDD_ZPROGRAM/`를 복사 → 폴더명 변경 → 이 `REPORT.md`를 채운다.
> 근거 표기(FS §N)는 [`../../standards/ABAP_CODE_STANDARD.md`](../../standards/ABAP_CODE_STANDARD.md) 섹션 번호를 가리킨다.

| 항목 | 내용 |
| --- | --- |
| 프로그램 ID / 명 | `Z...` / {한글명} |
| 모듈 | MM / SD / PP / FI ... |
| 입력 단위 | FORM / INCLUDE / PROG / METHOD |
| 적용 모드 | R / M / P (택1 이상, P는 단독 금지) |
| 대상 환경 | S/4 HANA |
| 작업일 | YYYY-MM-DD |
| As-Is 소스 | [`as-is/`](./as-is/) |
| To-Be 소스 | [`to-be/`](./to-be/) |

## 1. 📊 진단 요약

| 모드 | 발견 이슈 | HIGH | MID | LOW |
| --- | --- | --- | --- | --- |
| 🔧 R (가독성) | N건 | - | - | - |
| 🛠 M (유지보수) | N건 | - | - | - |
| ⚡ P (성능, 옵션) | N건 | - | - | - |

> **HIGH**: 데이터 오염/Silent Bug (BINARY SEARCH SORT 누락, CLEAR 누락 등)
> **MID**: 유지보수 비용 큰 항목 (FORM 분리, DRY 위반)
> **LOW**: 스타일 항목 (네이밍, 들여쓰기, 주석)

---

## 2. 🔄 As-Is vs To-Be 비교

### As-Is

```abap
* 원본 코드를 그대로 붙여넣기
* 삭제 예정 라인은 "❌[모드] 삭제: 사유 (Where-used: N건)" 주석으로 마킹
```

### To-Be

```abap
"=== 🔧[R][H1] {변경 단위 제목} ================================
" 변경: {What — 무엇을 바꿨는가}
" 이유: {Why — 왜 바꿨는가}
" 근거: FS §{N}
" 리스크: {없음 / 구체적 위험}
" Rollback: {git revert / 이전 패턴 복원 방법}
"================================================================
* 리팩토링 코드.
* 라인 단위 변경: " 🔧[R] was: ...  /  " ⚡[P][HIGH] ...  /  " 🛠[M] ...
* 신규 추가 라인: " ➕[모드] 신규: ...
* 한국어 주석은 100% 유지 (📌 의미 보존)
```

## 3. 📋 변경 사유 표

| # | 변경 항목 | 의도 | 근거 | 리스크 | Rollback |
|---|----------|-----|-----|-------|---------|
| 1 | JOIN alias k → a | 가독성 / FS 표준 일치 | FS §1 | 없음 | git revert |
| 2 | LOOP INTO → ASSIGNING | 성능 (복사 제거) | FS §3 | 원본 CLEAR 정책 유지 | 이전 LOOP 패턴 복원 |
| 3 | SORT 추가 (BINARY SEARCH 전) | Silent Bug 차단 | FS §6 | 없음 | SORT 라인 제거 |

> 각 행 = 하나의 원자적 변경 단위. 코드 내 변경 주석과 1:1 대응.
